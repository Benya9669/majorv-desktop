# Individual EQ на Marshall Major V

Выбор пресета и изменение полос идут по двум каналам. Пресет Individual приложение выбирает через BLE GATT. Усиление полос передаёт через Airoha RACE поверх Bluetooth Classic SPP/RFCOMM. UUID сервиса SPP в приложении — `00000000-0000-0000-0099-AABBCCDDEEFF`. Канал RFCOMM 21 наблюдался в одном захвате. При подключении настольному клиенту следует определять канал через обнаружение сервиса.

## Что отправляет приложение

При движении одного ползунка приложение передаёт значения всех пяти полос в Airoha SDK. Android-ветка для Major V называется `PLANT`. Частоты полос — 160, 400, 1000, 2500 и 6250 Гц. Для первых двух Q равен 0,7, для остальных — 1,0. Положение ползунка от 0 до 100 линейно соответствует диапазону от −6 до +6 дБ с шагом 0,12 дБ.

Приложение вызывает `PEQControl.setEQSetting` для пользовательской категории 101. Во время движения оно ограничивает частоту обновлений интервалом 100 мс и передаёт флаг `SaveOrNot=false`. Через 1,5 секунды после последнего изменения вызывает тот же метод с `SaveOrNot=true`. SDK готовит коэффициенты для 44,1, 48, 88,2 и 96 кГц.

## Как проверить по сохранённому HCI-захвату

Номера ниже соответствуют кадрам Wireshark в исходном исследовательском захвате. Кадры 7645 и 9129 отмечают выбор Individual и возврат к Marshall через GATT. Между ними на RFCOMM наблюдаются 34 команды `0x0E2B` по 199 байт, 34 команды `0x0E03` по 451 байту и 34 ответа на `0x0E03`. Размеры указаны для полных сообщений RACE. Кадр 8380 содержит оба сообщения подряд.

| Усиление 160 Гц | Кадр обновления | Кадры с данными последующей записи `0x0A01` |
|---|---:|---|
| +6 дБ | 8417 | 8462, 8478, 8500 |
| −6 дБ | 8619 | 8675, 8689, 8716 |
| 0 дБ | 9005 | 9018, 9032, 9058 |

В каждой группе три указанных кадра несут 185 + 8 байт параметров кривой и 444 байта данных DSP. В том же обмене есть дополнительные служебные записи. Ответы устройства подтверждают обмен. Сохранение после выключения наушников требует отдельной проверки.

## Формат для офлайн-декодера

Смещения ниже отсчитываются от первого байта полного сообщения RACE с нуля. В `0x0E2B` после шестибайтового заголовка идут 5 служебных байт, 10 записей по 18 байт и 8 завершающих байт. У Major V задействованы первые пять записей. Для полосы с индексом `i` частота лежит по смещению `13 + 18 × i` как `uint32LE` в сотых долях герца. Усиление лежит по смещению `17 + 18 × i` как `int32LE` в сотых долях дБ. Например, три строки таблицы дают +600, −600 и 0 для первой полосы.

В `0x0E03` блок DSP занимает 444 байта, от смещения 7 до конца сообщения. После четырёх байт в начале блока следуют четыре секции. Каждая содержит код частоты (`uint16LE`), число слов (`uint16LE`, здесь 53) и 53 слова по 16 бит. В этом захвате секции идут в порядке **44,1 → 96 → 48 → 88,2 кГц**, с кодами 1, 6, 2 и 5 соответственно. Для побайтового сравнения генератора важен именно этот порядок.

SHA-256 рассчитан по всем 444 байтам каждого блока DSP при нулевом усилении остальных четырёх полос. В каждой строке он также совпадает с SHA-256 сохранённых данных DSP из `0x0A01`.

| 160 Гц | Кадр `0x0E03` | SHA-256 от `msg[7:]` |
|---|---:|---|
| +6 дБ | 8418 | `f429bbdae666c4ba4ab8125f76d34987205438a54efba94d71514f840d10b3d1` |
| −6 дБ | 8620 | `882292ee31f61014b2d678f4b6b728536aef95dfbb44e7ffa8bda5ac6ae4d6b4` |
| 0 дБ | 9006 | `067f570d21087a60387b0e5238eb63244a97c742ded6d50a5a71cd6d78b56244` |

## Чтение пяти полос

В кадре 7196 телефон отправил фиксированный запрос RACE `05 5a 06 00 00 0a 00 ef e8 03` (команда `0x0A00`, ключ `0xEF00`). Ответ в кадре 7200 начинается с `05 5b bd 00 00 0a b9 00`. В нём 185 байт параметров, идентичных данным нулевой кривой из кадра 9018. Данные из кадров 8462 и 8675 отличаются от них только усилением первой полосы. Запрос происходит ещё до выбора пресета в кадре 7645.

Для записи с индексом `i` в полном 193-байтовом ответе частота находится по смещению `15 + 18 × i`, усиление — `19 + 18 × i`, Q — `27 + 18 × i`. Поля 32-разрядные, little-endian, в сотых единицы измерения. Усиление знаковое. Клиент сверяет тип, длину, частоты и параметры пяти активных фильтров до отображения результата.

**В приложении** подключите наушники и нажмите **Полосы Individual EQ**. Окно автоматически найдёт сопряжённые Major V через WinRT в Windows или BlueZ в Linux и прочитает профиль по Bluetooth Classic. Если система возвращает несколько подходящих пар, окно предложит выбрать наушники из списка. Если список пуст, выполните сопряжение наушников для воспроизведения звука в настройках ОС и нажмите **Повторить поиск**. В деморежиме окно показывает пять демонстрационных значений.

**В консоли** из корня проекта выполните команду для своей ОС. При нескольких подходящих устройствах в интерактивном терминале можно выбрать номер из списка. Для скриптов по-прежнему можно указать Classic-адрес после `read`.

```powershell
.\.venv\Scripts\python scripts/individual_eq.py read
```

```bash
.venv/bin/python scripts/individual_eq.py read
```

Подключение идёт по UUID. Флаг `--json` у команды `read` возвращает массив значений в дБ от 160 до 6250 Гц. Для пассивной проверки транспорта есть команда `probe`. Параметр `--timeout` задаёт время отдельно для подключения и ожидания ответа. [Подключение по UUID в Qt Bluetooth](https://doc.qt.io/qt-6/qbluetoothsocket.html#connectToService-1)

В Windows на физических Major V ранее проверено чтение нулевого профиля из консоли и QML-окна. После нового захвата наушники вернули −6, +6, +0,11, −6, +6 дБ. Устройство нашлось автоматически. При отдельном чтении трёх записей по UUID совпали все 637 байт с последним сохранением телефона, включая значение 506 сотых дБ для каждого канала и SHA-256 DSP из кадра 33258.

## Как снять обмен при чтении профиля на Android

1. В параметрах разработчика включите **Журнал Bluetooth HCI**. Если телефон предлагает режимы, выберите полный журнал. Выключите и снова включите Bluetooth, чтобы журнал содержал установление соединения. [Инструкция Android Open Source Project](https://source.android.com/docs/core/connect/bluetooth/verifying_debugging)
2. Откройте официальное приложение Marshall и подключите Major V. Запишите время подключения, время открытия экрана **Individual** и значения пяти полос, которые приложение показало до первого касания. Оставьте ползунки на месте. Важно сохранить обмен с момента подключения: приложение может загрузить профиль заранее.
3. Через несколько секунд закройте и снова откройте экран Individual. Отметьте время. Это даст второй интервал для сравнения и поможет заметить, использует ли приложение уже загруженные значения.
4. Сразу соберите отчёт об ошибке в параметрах разработчика или командой `adb bugreport` на подключённом ПК. Если в ZIP есть `FS/data/misc/bluetooth/logs/btsnoop_hci.log`, извлеките его. Когда журнал доступен только в текстовой части отчёта, используйте описанный в инструкции AOSP инструмент `btsnooz.py`. Проверьте наличие полезной нагрузки RFCOMM: состав отчёта зависит от устройства и режима журналирования. После сбора верните настройку журналирования в прежнее состояние.

Для анализа достаточно локального пути к HCI-логу и времени открытия экрана. Полный отчёт Android содержит другую диагностику телефона. Каталог `data/` в корне проекта исключён из Git.

## Разбор сохранённого обмена

Установив TShark, можно посмотреть запрос и ответ непосредственно в Android HCI-логе. Диапазон ниже соответствует исследовательскому захвату.

```shell
python -m scripts.inspect_eq_capture data/capture/btsnoop_hci.log --channel 21 --first-frame 7196 --last-frame 7200 --hex
```

Для другого захвата начните без фильтра канала и номеров кадров. Команда выводит номера кадров, направление и команды RACE. Если TShark отсутствует в PATH, передайте путь к исполняемому файлу через `--tshark`.

Для ручного разбора экспортируйте полезную нагрузку одного направления и одного RFCOMM-соединения в бинарный файл, начиная с границы RACE-сообщения. Уберите заголовки HCI, L2CAP и RFCOMM. Затем передайте файл декодеру из активированного окружения.

```shell
python scripts/individual_eq.py decode stream.bin
```

Декодер собирает сообщения по длине и различает полные обновления и короткие ответы с тем же ID. Для данных `0x0E2B` он проверяет частоты и показывает усиления. Для `0x0E03` проверяет коды четырёх частот дискретизации и длины секций, печатает SHA-256 и отмечает совпадения с таблицей выше.

## Генератор DSP

В захвате `majorv-all-bands.log` нашлись 248 пар запросов `0x0E2B` и `0x0E03` для 143 разных кривых. Генератор побайтово воспроизвёл все 248 блоков по 444 байта. Смешанным кривым соответствуют 65 обновлений для 48 разных сочетаний. В 28 обновлениях задействованы все пять полос. При остальных полосах на нуле каждая полоса по отдельности достигала и −6, и +6 дБ. Исходный захват дал ещё 34 совпадения для 24 положений первого ползунка.

Проверка по исходным файлам с установленным TShark

```shell
python -m scripts.inspect_eq_capture data/capture/majorv-all-bands.log --channel 21 --verify-dsp
python -m scripts.inspect_eq_capture data/capture/btsnoop_hci.log --channel 21 --verify-dsp
```

SDK переводит позицию ползунка 0…100 в усиление с арифметикой float32. Например, для позиции 51 номинал равен +0,12 дБ, а в параметрах сохраняется +0,11 дБ. Каскады фильтров идут по убыванию усиления. При равенстве усилений первой идёт меньшая частота. Коэффициенты упакованы как знаковые 24-разрядные значения в двух 16-разрядных словах. Масштаб первого каскада 1/1,19 компенсируется в итоговом усилении. В новом захвате секции идут в порядке 88,2 → 44,1 → 48 → 96 кГц.

Например, команда ниже воспроизводит DSP в кадре 33258 для кривой −6, +6, +0,12, −6, +6 дБ. Ожидаемый SHA-256 равен `1e25cd9f595efe6104e923e6a3abde576493b55d5e00fa5c6b922631df1c0267`. Один аргумент по-прежнему воспроизводит исходный проход по полосе 160 Гц.

```shell
python -m scripts.individual_eq_dsp 0 100 51 0 100
```

## Запись и обратное чтение

Выберите пресет **Individual**, откройте **Полосы Individual EQ**, отредактируйте ползунки и нажмите **Применить**. Приложение сравнит текущие настройки наушников с теми, которые вы открыли. Если за это время профиль изменился, перечитайте его перед повтором. В конце редактор покажет фактически прочитанные значения в дБ, поэтому отображение может отличаться от номинала на 0,01 дБ.

Из консоли ту же кривую можно записать с автоматическим выбором сопряжённой пары. Значения для `--bands` указываются в дБ, по возрастанию частоты. Команда `apply` меняет настройки наушников.

```shell
python scripts/individual_eq.py apply --bands -6 6 0.12 -6 6
python scripts/individual_eq.py read
```

Клиент проверяет исходные параметры и карту банка EQ, ждёт ответ на каждом этапе и в конце перечитывает три записи: 185 байт параметров (`EF00`), 8 байт запаса усиления (`EF20`) и 444 байта DSP (`E42C`). Если связь прервалась, перечитайте профиль. Даже если усиления уже успели сохраниться, после неудачной записи можно нажать **Применить** повторно.

Для `EF20` клиент оценивает пик АЧХ квантованных фильтров при 44,1 кГц на сетке с шагом 4 Гц. Полученные значения обоих каналов совпали для всех 248 обновлений. Во всех 28 завершённых сохранениях нового захвата совпала последовательность запросов, включая шесть сохранений смешанных кривых. Отдельной аппаратной проверкой остаются запись из настольного приложения и повторное чтение после выключения и включения наушников. [Как собрать новый захват на Android](capture-all-bands.md)
